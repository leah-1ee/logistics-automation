# 01. 제품 PRD

## 1. 목표와 우선순위

우선순위는 ① JD와 연결되는 물류 업무 자동화 ② 실제 주문 데이터 처리와 검증 ③ 임베디드 단말 연동 ④ AI 활용 실험입니다.

운영자는 외부 주문을 다시 입력하지 않고, 시스템이 생성한 출고 작업을 확인·배정합니다. 작업자는 배정된 상품을 스캔합니다. 서버나 통신이 일시 중단돼도 이미 받은 작업의 기록을 계속 남기며, 복구 후 자동 동기화합니다. 정상 건은 자동 처리하고 보류·실패·충돌 건에 운영자의 주의를 모읍니다.

## 2. 문제 정의와 근거의 범위

물류 주문 수집, 창고별 데이터 형식 변환, 출고 요청, 처리 결과 수신, 예외 재처리는 실제 물류 연동의 구성 요소입니다. 본 프로젝트는 이 구조를 공개 주문 데이터와 모의 창고 작업으로 재현합니다.

다음은 프로젝트가 검증할 문제 가설입니다.

| 가설 | 구현으로 바꿀 행동 | 검증 방식 |
| --- | --- | --- |
| 주문을 다시 입력하고 작업을 생성하는 반복을 줄일 수 있다 | 유효 주문에서 출고 작업 자동 생성 | 원본 주문·생성 작업의 대응과 수동 개입 수 |
| 통신 문제 때문에 현장 기록을 다시 작성할 필요를 줄일 수 있다 | SQLite 보존·복구·자동 전송 | 단절·재시작 전후 기록 일치 |
| 재시도 때문에 같은 주문·스캔이 두 번 반영되는 문제를 방지할 수 있다 | DB 제약·트랜잭션·이벤트 ID | 응답 유실·중복 전달 시 최종 수량 |
| 운영자가 처리 대상 전체를 반복 확인하는 부담을 줄일 수 있다 | 예외 중심 어드민·자동 집계 | 예외 분류 결과·직접 수행한 수동 비교 실험 |

특정 기업이 현재 이 업무를 수작업으로 수행한다거나, 이 프로젝트가 기존 상용 제품보다 뛰어나다고 전제하지 않습니다. 생산 운영 환경의 효율 개선 수치는 실제 사용 없이 주장하지 않습니다.

## 3. JD 연결

| 요구 역량 | MVP 증거 | 첫 확장 증거 |
| --- | --- | --- |
| TypeScript·NestJS·MikroORM·MySQL·Redis | 모듈 분리, 주문 저장, 트랜잭션, 큐 처리 | 배치 최적화, 워커 확장, Redis 복구 |
| REST/Open API 수집·적재·가공 | 별도 모의 외부 API의 커서 수집·정규화 | API 어댑터·실제 외부 샌드박스 연동 |
| 업무 자동화·시스템화 | 주문 검증→작업 생성→집계, 자동 동기화 | 자동 배정·묶음 피킹·조건별 알림 |
| 유지보수 가능한 코드 | 도메인 규칙과 외부 연동 분리·계약·테스트 | 외부 연동 교체와 회귀 검증 |
| Internal Product | 검색, 배정, 보류 사유, 이벤트 이력, 재처리 | 대량 조치, 권한, 운영 지표 |
| 현장 문제와 운영 흐름 | 실제 QR 입력, 오류 안내, 오프라인 복구 | 다중 단말과 현장 정책 |
| 서로 다른 OS | 공통 웹 화면·HTTP 계약, Linux 보드 시연 | 사용 가능한 Windows 등에서 같은 흐름 검증 |

모의 API는 실제 외부 서비스와의 운영 연동 실적이 아닙니다. 이 차이는 포트폴리오와 결과 보고서에 표시합니다.

## 4. 사용자와 핵심 흐름

### 운영자

수집 결과와 보류 주문을 확인하고, 출고 작업을 한 단말에 배정합니다. 진행·동기화·오류 상태를 조회하고 실패한 서버 작업을 재시도합니다. 완료 수량을 일별·상품별로 확인합니다.

### 현장 작업자

단말에서 배정된 스냅샷을 내려받고, 실제 QR을 스캔합니다. 잘못된 상품·초과 수량을 즉시 확인하며, 잘못 스캔한 건은 해당 스캔을 되돌립니다. 모든 수량이 맞으면 완료 기록을 남깁니다.

### 검증자/개발자

동일 데이터와 고정 시드의 시나리오를 재생하고, 원본·단말·서버·집계가 맞는지 확인합니다. 정상과 장애 시험, 시뮬레이션과 실제 보드 실험을 구분해 기록합니다.

## 5. MVP 경계

| 포함 | 이후 확장 |
| --- | --- |
| Olist 주문·상품·주문 상품 전체 적재 | 결제·리뷰 등 추가 활용 |
| 유효한 단일 판매자 주문의 작업 생성 | 다중 판매자 분할 작업 |
| 수동 배정, 단말 1대 | 자동 배정·다중 단말·재배정 |
| 스캔·스캔 취소·완료 기록 | 상품 변경·부분 출고·반품 |
| SQLite 보존과 자동 동기화 | 장시간·대규모 동기화 최적화 |
| 서버 큐 1개, 워커 1개, 작은 outbox와 복구 루프 | 큐 분리·워커 확장·캐시 최적화 |
| 예외 조회·서버 작업 재시도·사유 기록 | 업무 충돌의 정식 정정·승인 절차 |
| 일일·상품별 집계와 CSV | 분석 저장소·다차원 리포트 |

실재고·재고 예약, 실제 결제·택배 발송, 고객 개인정보 관리, 로봇팔 제어, 온디바이스 대형 모델, AI 파손 검사, 마이크로서비스 분리는 MVP 범위 밖입니다.

## 6. 핵심 불변 조건

1. 동일 출처·동일 원본 주문은 한 번만 정규화됩니다.
2. MVP의 적격 주문 하나에 출고 작업 하나만 생깁니다.
3. 스캔 수량은 0 이상, 필요 수량 이하입니다.
4. 하나의 스캔은 한 번만 되돌릴 수 있습니다.
5. 완료 확정 시 모든 상품 수량이 일치합니다.
6. 이벤트 중복 전달이 결과를 다시 바꾸지 않습니다.
7. 서버 반영 완료는 영구 기록 커밋 이후에만 표시합니다.
8. 로컬 미전송 기록은 앱·보드 재시작으로 사라지지 않습니다.
9. 동일 작업의 정상·중복 완료를 다시 받아도 집계에 한 번만 포함합니다.
10. 원본 사실과 시뮬레이션 상태·생성 데이터를 혼합해 실적이라고 보고하지 않습니다.

## 7. 목표와 측정

정확성은 06 문서의 통과/실패 조건으로 평가합니다. 처리량·지연·수동 시간은 측정값으로 보고하고 미측정 수치를 목표 달성 실적으로 쓰지 않습니다.

약 10만 건이라는 누적 크기만으로 고트래픽 운영 경험이라고 표현하지 않습니다. 원본 전체 처리, 압축 재생에 의한 순간 유입, ID를 바꾼 파생 데이터는 서로 다른 시험입니다.

## 8. 제품의 결과물

실행 가능한 모듈형 서비스와 단말, 재현 가능한 데이터 준비·시험 절차, 검증 보고서, 짧은 시연 영상, 설계 결정·트레이드오프 문서가 개발 단계의 산출물입니다. 현재 패키지는 그 산출물을 만들기 위한 PRD이며 구현 완료 보고서가 아닙니다.
