# 02. MVP 기능 및 수용 기준

요구 ID는 테스트·커밋·완료 보고서에서 그대로 사용합니다. P0는 MVP 필수입니다.

## 1. 데이터·주문

| ID | 요구 사항 | 수용 기준 |
| --- | --- | --- |
| M-D01 | 원본 파일·버전·해시·행 수를 보존 | 준비 manifest에서 재실행 입력 확인 가능 |
| M-D02 | 전체 원본 주문·상품·주문 상품 수집 | 원본 키 기준 수집·보류·제외 합계 대사 통과 |
| M-D03 | 별도 모의 외부 REST API를 커서 방식으로 수집 | 같은 페이지 재수집 시 주문 수 불변 |
| M-D04 | 배치별 체크포인트 저장 | 중간 종료 후 재개 결과가 처음부터 실행한 결과와 같음 |
| M-D05 | 형식 오류와 부적격 주문 구분 | INVALID_DATA·UNSUPPORTED·READY 사유별 집계 |
| M-D06 | 정규화 수정과 원본 불변성 구분 | 원본은 수정하지 않고 정정 기록과 새 처리 버전 보존 |

수정은 작업 생성 전 데이터 보류 건에서만 허용합니다. 상품 ID·수량 등 작업 의미가 바뀌는 수정은 새 정규화 revision을 만들고 운영자 사유를 요구합니다. 이미 배정된 작업 스냅샷의 직접 변경은 차단합니다. 실제 원본 주문의 취소·주소 변경을 재현했다고 주장하지 않습니다.

## 2. 작업 생성과 배정

| ID | 요구 사항 | 수용 기준 |
| --- | --- | --- |
| M-W01 | READY 주문에서 비동기 출고 작업 생성 | 적격 주문마다 작업 하나, 상품별 수량 정확 |
| M-W02 | 작은 DB outbox와 재스캔으로 작업 전달 복구 | Redis 중단 후 복구 시 누락 작업 생성 |
| M-W03 | 운영자가 단말에 작업 배정 | 미배정 작업만 배정되고 단말 소유권 기록 |
| M-W04 | 단말이 불변 스냅샷 내려받기 | taskId·assignmentVersion·상품·수량·해시 보존 |
| M-W05 | 배정 후 상품·수량·단말 변경 차단 | 연결이 없어도 이미 받은 스냅샷의 의미 유지 |
| M-W06 | 데이터 보류 사유·운영 메모 조회 | 관련 주문·작업·이벤트로 이동 가능 |

단말에는 여러 작업을 배정할 수 있지만 한 번에 한 작업만 열어 처리합니다. 배정 시각 이후 자동 만료·자동 재배정은 없습니다.

## 3. 현장 단말

| ID | 요구 사항 | 수용 기준 |
| --- | --- | --- |
| M-E01 | 실제 QR 입력 | Raspberry Pi에 연결한 카메라 또는 USB 스캐너로 확인 |
| M-E02 | 잘못된 상품·형식·초과 수량 경고 | 수량·정상 이벤트 시퀀스가 증가하지 않음 |
| M-E03 | 정상 스캔은 한 개씩 증가 | 각 입력에 UUID eventId, 작업별 연속 seq 생성 |
| M-E04 | 특정 스캔 되돌리기 | 이전 SCAN_ITEM을 참조하는 REVERSE_SCAN, 중복 취소 방지 |
| M-E05 | 필요 수량 일치 시 완료 | 불일치 상태에서 완료 버튼 비활성화 |
| M-E06 | SQLite에 상태·이벤트·전송 대기 동시 저장 | 저장 중 강제 종료 시 일부만 남는 상태 없음 |
| M-E07 | 재부팅 후 작업 복구 | 카운트·스캔 취소 이력·전송 상태 복구 |
| M-E08 | 로컬 완료와 서버 확정 표시 분리 | 완료 후에도 미동기화 표시는 유지 |

정상 스캔 취소는 COMPLETE 기록 전까지 가능합니다. COMPLETE 이후에는 스냅샷을 잠그며 새로운 스캔·취소를 받지 않습니다. 중복 물리 입력은 같은 상품이라도 별도 이벤트입니다. 수량 한도 검사는 가능하지만 개별 물품의 일련번호가 없으므로 같은 실물을 두 번 찍었는지는 증명할 수 없습니다.

## 4. 동기화

| ID | 요구 사항 | 수용 기준 |
| --- | --- | --- |
| M-S01 | 이벤트 단위 DB 반영 이후 ACK | ACK된 이벤트가 서버 재시작 후에도 존재 |
| M-S02 | 중복 ID·같은 내용 재전송 | 최초 결과 반환, 수량·상태·집계 불변 |
| M-S03 | 같은 ID·다른 내용 거부 | EVENT_ID_REUSED, 해당 작업 전송 중지·운영 알림 |
| M-S04 | 작업별 seq 순서 적용 | 누락 앞 순서가 도착하기 전 다음 이벤트 미적용 |
| M-S05 | 단말 소유권·배정 버전 확인 | 다른 단말·과거 버전이 정상 결과를 바꾸지 않음 |
| M-S06 | 일시 오류 재시도 | 지수 대기·jitter, 수동 재시도 가능 |
| M-S07 | 업무 오류 격리 | 문제 작업만 차단하고 다른 작업 전송 지속 |
| M-S08 | ACK 유실·부분 배치 결과 복구 | 서버 결과가 한 번만 적용되고 남은 이벤트 재전송 |

이벤트는 최소 한 번 전달될 수 있습니다. 네트워크 수준의 exactly-once를 약속하지 않습니다. 중복 전달 후에도 DB의 업무 반영 효과가 한 번이 되도록 만듭니다.

## 5. 운영 어드민

| ID | 화면/기능 | 필요한 정보·행동 |
| --- | --- | --- |
| M-A01 | 주문 목록·상세 | 원본 ID, source 상태, 정규화 상태·revision, 제외/보류 이유 |
| M-A02 | 작업 목록·상세 | 서버 상태, 단말, 상품별 수량, 이벤트 이력, 운영 메모 |
| M-A03 | 배정 | 미배정 작업 선택→단말 선택→확인 |
| M-A04 | 서버 처리 작업 | 대기·처리 중·실패, 시도 횟수, 최근 오류, 재시도 |
| M-A05 | 단말 상태 | 마지막 통신, 미전송 수·가장 오래된 기록, 앱 버전 |
| M-A06 | 보고서 | 업무 기준일별 완료 작업·상품 수량, 미확정 제외, CSV |
| M-A07 | 기본 인증·감사 | 등록된 운영자/단말만 접근, 변경자·시각·사유 기록 |

오프라인 단말의 현재 미전송 수를 서버가 실시간으로 안다고 표시하지 않습니다. 가장 최근 단말 보고 값과 관측 시각을 함께 표시하고 오래된 값은 stale로 표시합니다.

## 6. 서버 상태

### 주문

- RECEIVED: 원본을 영구 저장함.
- DATA_HOLD: 변환·검증에 필요한 정보가 없거나 잘못됨. 작업 미생성.
- UNSUPPORTED: MVP 범위 밖. 원본 보존, 작업 미생성.
- READY: 정규화 통과, 작업 생성 요청이 DB에 기록됨.
- TASK_CREATED: 연결된 작업 존재.

DATA_HOLD는 운영자가 실제 근거로 정규화 값을 정정한 뒤 재검증할 수 있습니다. UNSUPPORTED는 확장 기능 도입 전 강제 통과시키지 않습니다.

### 출고 작업

~~~mermaid
stateDiagram-v2
    [*] --> CREATED
    CREATED --> ASSIGNED: 배정
    ASSIGNED --> IN_PROGRESS: 첫 유효 스캔
    IN_PROGRESS --> CONFIRMED: COMPLETE 검증 통과
    ASSIGNED --> HOLD: 유효 형식의 업무 충돌
    IN_PROGRESS --> HOLD: 유효 형식의 업무 충돌
    CONFIRMED --> [*]
~~~

HOLD에 대한 이벤트는 이후 무조건 통과시키지 않습니다. MVP에서는 사유 확인·메모·안전한 서버 작업 재시도만 제공합니다. 잘못된 업무 기록의 정정·재배정·강제 완료는 E2의 승인 절차로 확장합니다. 전송 오류만으로 작업 상태를 HOLD로 바꾸지는 않습니다.

### 단말 상태

DOWNLOADED → IN_PROGRESS → LOCAL_COMPLETED → SERVER_CONFIRMED. 완료 전 수량이 0으로 되돌아가도 IN_PROGRESS를 유지합니다. 동기화 오류는 별도 syncStatus(SYNCED/PENDING/RETRYING/BLOCKED)로 표시합니다.

## 7. 비기능 기준

- API는 UTC의 offset 포함 ISO-8601 시각을 사용하며 업무 기준 시간대는 설정값입니다.
- 원본 시간대가 불명확한 Olist 시각은 05 문서의 가상 시계로 처리합니다.
- 큐·로그에는 주문 본문 전체 대신 DB 식별자를 우선 넣습니다.
- SQLite는 실제 파일 저장소를 사용하고 임시 브라우저 저장만으로 성공 처리하지 않습니다.
- 네트워크 재시도·로딩·검수 상태를 작업자가 구분할 수 있어야 합니다.
- 읽기 목록은 페이지 단위입니다. 무제한 전체 조회 API를 만들지 않습니다.
- 서버/단말은 상태 확인 endpoint를 제공하고 종료 중 새 작업 수락을 조절합니다.
