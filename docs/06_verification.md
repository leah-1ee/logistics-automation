# 06. 검증·성능·장애 시험

## 1. 완료 판정

MVP 완료는 M-* 요구 사항과 아래 T-* 필수 시험 통과로 판정합니다. UI가 뜨거나 API가 200을 반환하는 것만으로 완료하지 않습니다.

원본 다운로드·실제 하드웨어·소프트웨어 재생·파생 부하를 구분합니다. 시험을 아직 하지 않았으면 NOT_RUN, 장비가 없어 못 했으면 BLOCKED로 적습니다. 이를 PASS로 바꾸지 않습니다.

## 3. 데이터 단계

| 단계 | 입력 | 목적 | 완료 기준 |
| --- | --- | --- | --- |
| F0 | 작은 고정 fixture | 도메인·ACK·변환 규칙 단위 검증 | 예측 가능한 정답과 일치 |
| F1 | 실제 원본에서 적격 1,000주문 선정 | 기능·장애 자동 재생 | T27, 실패 조건 시 재현 가능 |
| F2 | Olist 전체 원본 | 실제 규모의 수집·검증·조회·작업 생성 | T28, 정확한 분모·제외 사유 보고 |
| F3 | 같은 원본을 압축 재생 | 순간 유입·backpressure | 처리량·지연·큐 복구를 측정 |
| F4 | 원본 기반 파생 100만 주문 | 장시간·저장량 증가 | 합성/파생 표시, 관계·분포 보존 검증 |

F0~F2가 MVP 필수, F3는 E1 필수, F4는 선택 확장입니다. F2는 원본 전체에서 모든 현장 작업을 손으로 스캔하라는 요구가 아닙니다. 전체 수집·정규화·작업 생성을 자동 검증하고 F1·T29로 작업 이벤트와 실제 단말을 확인합니다.

F4에서는 주문·상품·판매자 key를 일관되게 remap하고 run을 격리합니다. 단순 같은 ID 복제는 중복 방지 시험이지 100만 독립 주문 처리 시험이 아닙니다.

## 4. 성능 실험

초기 입력률은 환경에서 정상 완료되는 낮은 수준부터 높입니다. 워커 1→2→4, batch size 50→200→500 같은 설정은 실험 변수 예시이며 고정 성공 목표가 아닙니다.

입력률·동시 사용자·단말 수·워커 수·DB 연결 수·배치 크기를 한 번에 모두 바꾸지 않습니다. warm-up, 측정 구간, 큐 drain 구간, 반복 횟수를 사전에 고정하고 적어도 기준 실험과 개선 실험은 같은 장비·입력으로 비교합니다.

| 지표 | 정의 |
| --- | --- |
| ingestion rate | 원본 주문 영구 저장 건수 / 측정 초 |
| task throughput | 고유 작업 생성 또는 확정 건수 / 측정 초. 둘을 분리 |
| API latency p50/p95/p99 | 요청 시작→응답 수신. 실패·timeout도 별도 집계 |
| end-to-end latency | 원본 공개→출고 작업 사용 가능. 현장 완료 지연과 구분 |
| sync latency | local event 커밋→서버 적용 확인. 오프라인 시간을 포함/제외한 값 구분 |
| queue depth | 현재 대기 job 수 |
| oldest job age | 가장 오래 기다린 미완료 job의 나이 |
| recovery drain time | 장애 복구→미처리 대기열과 정합성 검사 정상화까지 |
| memory/CPU/DB | peak RSS, CPU, DB query 수·시간·연결·잠금 대기 |
| duplicate deliveries | 재전송·중복 실행 횟수 |
| duplicate effects | 실제 중복 task·카운트·집계 반영 수. 목표 0 |
| lost acknowledged events | ACK 성공 후 DB에서 찾지 못하는 event 수. 목표 0 |

처리량만 증가했더라도 큐가 계속 늘면 안정적으로 감당한 입력률이라고 쓰지 않습니다. 지연 허용치는 기준 측정 후 명시하고 결과에 맞춰 사후 변경하지 않습니다. 장비·리소스·데이터 크기·설정 없이 TPS만 보고하지 않습니다.

## 5. 장애 주입

faultPlan에는 대상 component, 발생 trigger, 지속 조건, seed, 복구 조건을 기록합니다. trigger는 이벤트 번호·DB 커밋 직후·워커 job 상태 등 재현 가능한 지점을 사용합니다.

예시 계획:

- API 5xx/timeout/429와 응답 유실.
- SQLite·MySQL 쓰기 실패와 프로세스 종료.
- Redis 연결 불가·워커 종료·발행 후 상태 기록 전 종료.
- 동일 이벤트 중복, 순서 역전, 특정 seq 지연.
- 단말 전원/프로그램 재시작과 시계 오차.

실제 SD카드 쓰기 실패·디스크 손상까지 무제한 보장을 선언하지 않습니다. 시험한 장애와 한계를 구체적으로 기록합니다.

## 6. 업무 자동화 평가

고정 주문 묶음에서 수동 입력·작업 생성·집계를 직접 수행한 baseline과 자동화를 비교할 수 있습니다. 가능하면 같은 작업 정의·입력으로 반복하고, 학습 효과를 고려해 순서를 섞습니다.

자동 처리율 = 운영자 수정·개입 없이 목표 상태에 도달한 적격 주문 수 / 적격 주문 수.

분모에서 부적격·오류·미지원 건을 제거했으면 그 개수도 함께 보고합니다. 출고 작업 자동 생성률과 실제 현장 피킹 자동화율은 다릅니다. 스캔을 사람이 하면 피킹 자체가 자동화됐다고 쓰지 않습니다.

합성 장애의 예외 처리율과 실제 원본 품질 보류율은 별도 지표입니다. 시뮬레이션 결과를 실제 고객·직원의 절감 시간으로 확대하지 않습니다.

## 7. 보고서 템플릿

각 run마다 다음 파일/값을 남깁니다.

1. 코드 commit, lockfile hash, DB migration version.
2. dataset/scenario/fault manifest와 해시.
3. 장비·OS·CPU·메모리·저장소·네트워크·시간대.
4. 원본/적격/보류/제외/생성/확정/미확정 건수.
5. 이벤트 생성·수신·반영·중복·거부·미확인 수.
6. DB 정합성 검사와 집계 대사 결과.
7. 성능 지표와 오류 분포.
8. T-*별 PASS/FAIL/BLOCKED/NOT_RUN과 증거 경로.
9. 알려진 한계와 재현 명령.

PRD 패키지에는 보고서 작성 기준만 있습니다. 실제 PASS 결과나 성능 수치를 생성해 놓지 않습니다.

구현 보완(2026-10-28): 전체 대사는 서버 raw DTO만을 정답으로 재사용하지 않습니다.
불변 CSV 해시를 재확인하고 준비 인덱스의 원본 주문/상품 행·상품 속성과 각각 대조합니다.
서버 원본 DTO와 task 수량이 같은 방식으로 잘못 변한 경우도 FAIL이어야 합니다.
독립 재검증 보완: raw payload의 canonical hash 및 정규화 order_items 수량이
각각 단독으로 손상된 경우도 FAIL이어야 합니다. 별도 CSV 직접 파서는 Source/normalize/
기존 reconcile을 호출하지 않고 원본 분류·수량·스냅샷·이벤트·집계를 확인합니다.
서버 조회는 200개 단위로 묶어 대사 도구가 작업마다 여러 왕복 요청을 만들지 않게 하며,
원본 분류·스캔 순수 합계·일별/상품별 집계와 누락 집계 날짜도 확인합니다.
