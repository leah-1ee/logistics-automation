# 07. 개발 순서와 완료 체크리스트

## 1. 진행 원칙

개발은 단계별로 작은 실행 가능한 결과를 남깁니다. 기능을 만들 때 해당 T-* 시험도 함께 통과시킵니다. 다만 네트워크·Redis·하드웨어 같은 통합 장애 검증은 마지막 통합 단계에서도 확인합니다.

MVP의 서버 큐·DB 중복 방지·작은 outbox는 기본 설계입니다. E1은 이를 더 큰 부하와 장애 조건에서 강화하는 단계입니다.

| 단계 | 작업 | 산출물 | 다음 단계 진입 조건 |
| --- | --- | --- | --- |
| S0 계약·환경 | 문서 정합성 확인, 안정 라이브러리 버전 고정, 모듈 구조·Compose·migration·인증 skeleton | 빈 서비스·DB·Redis·health·CI | 원클릭 개발 환경, /health와 인증 시험 |
| S1 실제 데이터 | 원본 다운로드 절차·manifest·필드 검증·source API·cursor·checkpoint | 전체 수집기·품질 보고서 | T01~T04·T32, 전체 원본 대사 |
| S2 업무 모델 | 정상 주문→작업, 작은 outbox·워커·배정·snapshot hash | 주문·작업 API와 task 생성 job | T05~T07·T20~T22 |
| S3 단말 로컬 | SQLite schema, 상태 projection, QR·스캔·취소·완료 | 로컬 API와 최소 작업 화면 | T08~T13, 실제 QR 입력 확인 |
| S4 동기화 | batch·receipt·hash·seq·idempotency·retry·격리 | 서버 이벤트 처리와 로컬 sync worker | T14~T19·T23·T25 |
| S5 어드민·집계 | 검색·배정·이벤트·실패 job·재시도·메모·일별 집계·CSV | 운영 화면, 재처리·감사 | T24·T26·T30~T31·T33 |
| S6 통합 검증 | 1,000작업 재생·전체 import·장애 재현·보드 재시작 | T-* 결과표·보고서·시연 | T01~T34 전부 PASS |
| S7 MVP 마감 | README·실행 절차·정책·한계·데모·release tag | mvp-v1 결과물 | 확장 착수 전 MVP 재현 가능 |

## 2. 일주일 실행 계획 예시

아래는 보유 장비와 기존 개발 경험이 있다는 전제의 배분 예시입니다. 일정 약속이나 완료 보장이 아닙니다. 데이터 접근·보드 환경·예상하지 못한 오류가 지연되면 확장 개발은 시작하지 않습니다.

| 작업일 | 주력 | 완료할 좁은 흐름 |
| --- | --- | --- |
| D1 | S0·S1 | 원본→모의 API→DB 대사 |
| D2 | S2 | 주문→작업→배정 스냅샷 |
| D3 | S3 | 로컬 스캔·취소·완료·재시작 복구 |
| D4 | S4 | 온라인 동기화·응답 유실·중복 방지 |
| D5 | S5 | 운영 어드민·집계·예외 확인 |
| D6 | S6 | 전체 데이터·장애·보드 시험 |
| D7 | 수정·S7 | 실패 수정·보고서·데모·release |

시간이 부족할 때 줄일 것: 시각 효과, 대시보드 차트, 배치 크기 미세 튜닝, 여러 입력 장치, 후속 AI 기능.

유지할 것: 실제 데이터 출처, 원본 대사, 스캔·취소·완료 규칙, SQLite 보존, ACK 의미, DB 중복 방지, 복구 증거, 실제 보드 입력.

## 3. 개발 작업 티켓의 기본 형태

- 연결 요구 ID와 테스트 ID.
- 기능의 입력·출력·실패 조건.
- 변경 모듈·migration·API 계약 변경 여부.
- 완료 증거: 실행 결과, 정합성 검사, 필요한 화면.
- 되돌릴 때 데이터에 미치는 영향.

함수/모듈 단위 작은 커밋을 남기되 도메인 상태·schema·계약을 서로 다른 모순 상태로 오래 두지 않습니다. 실제 테스트하지 않은 내용을 커밋 메시지나 보고서에 PASS로 적지 않습니다.

## 4. AI 개발 활용 실험

코딩 에이전트는 이 문서 세트를 컨텍스트로 사용할 수 있습니다. 실제 실행 여부와 도구는 개발 환경에서 선택합니다. 본 문서 작성 과정에서 개발 에이전트를 실행했다는 의미는 아닙니다.

구현 세션과 독립 검증 세션을 구분합니다. 검증 세션에는 요구 사항·API·변경 diff·시험 결과를 제공하고 실제 누락·경계 조건을 확인하게 합니다. 같은 모델을 써도 역할·세션은 분리할 수 있으며, 효과는 발견된 실제 결함·오탐·시간·비용으로 평가합니다.

모델의 승인 문장만으로 병합하지 않습니다. 이벤트 재전송·순서·DB 제약·복구는 실행한 검증 증거로 판정합니다. 자동 push/PR 제출/외부 계정 변경은 프로젝트 개발 시 사용자가 정한 권한 범위에 따릅니다.

## 5. MVP 종료 체크리스트

- [ ] 원본 manifest·해시·정확한 규모가 기록돼 있습니다.
- [ ] 원본 전체 수집/분류/작업 생성 대사가 맞습니다.
- [ ] 다른 source·datasetRun 데이터가 섞이지 않습니다.
- [ ] 카메라 또는 USB 스캐너로 실제 QR 입력이 됩니다.
- [ ] 잘못된 입력·스캔 취소·불완전 완료가 처리됩니다.
- [ ] 단말 재시작 후 로컬 이벤트와 수량이 복원됩니다.
- [ ] 네트워크 단절 중에도 내려받은 작업 기록이 됩니다.
- [ ] 커밋 후 응답 유실·중복·순서 역전 시험이 통과합니다.
- [ ] Redis 중단 후 서버 작업 누락이 복구됩니다.
- [ ] 하나의 차단 작업이 다른 작업의 전송을 막지 않습니다.
- [ ] 집계는 CONFIRMED 기준이며 반복 실행 결과가 같습니다.
- [ ] 어드민에서 오류·재처리·이력을 확인할 수 있습니다.
- [ ] 토큰·권한·허용 origin·감사 시험이 통과합니다.
- [ ] 1,000작업 자동 재생과 실제 보드 시연 증거가 별도입니다.
- [ ] 성능 수치와 시험 환경·한계가 기록돼 있습니다.
- [ ] T01~T34에 FAIL/BLOCKED/NOT_RUN이 남아 있지 않습니다.
- [ ] 깨끗한 환경에서 재현 가능한 실행·데이터 준비·시험 절차가 있습니다.

보드 사용이 불가능한 경우 소프트웨어 MVP로만 표시하고 전체 MVP 완료로 기록하지 않습니다.

## 6. 확장 진입·변경 관리

MVP tag와 baseline 보고서를 보존한 뒤 E1 브랜치/마일스톤을 시작합니다. 각 확장은 아래 세 가지를 먼저 정합니다.

1. 해결할 병목·업무 문제와 기존 측정값.
2. 개선 목표·정확성 유지 조건·추가 리스크.
3. 이전 버전으로 복구할 데이터·기능 전환 계획.

DB schema·이벤트 계약·snapshotVersion을 바꾸면 지원 버전·migration·구버전 단말 정책을 문서와 시험에 함께 추가합니다. 요구 사항을 바꿨다면 결과 보고서도 새 기준으로 다시 작성합니다.
