# 08. 확장 로드맵과 개별 개발 범위

## 1. 단계 개요

| 단계 | 목적 | 필수 선행 조건 | 우선순위 |
| --- | --- | --- | --- |
| E1 | 대량 처리·운영 복구와 측정 | MVP·전체 원본 대사·baseline | JD 연결이 높아 첫 확장 |
| E2 | 실제 업무 자동화·다중 단말 | E1 정확성·상태/배정 정책 | JD 연결이 높음 |
| E3 | 입고·재고·반품·실제 외부 연동 | 추가 데이터·정책·접근 권한 | 필요에 따라 선택 |
| E4 | AI 업무 보조·비전·분산 구조 | 비교 가능한 baseline·실제 필요 | 별도 실험 |

한 단계의 전 항목을 모두 구현해야 다음 단계로 넘어간다는 의미는 아닙니다. 항목별 의존성을 따르며 선택 이유를 기록합니다. 다중 단말의 권한·배정 버전 검증 같은 선행 조건은 생략하지 않습니다.

## 2. E1: 대량 수집과 Redis 심화

| ID | 확장 | 범위·해결할 문제 | 수용/검증 |
| --- | --- | --- | --- |
| E1-01 | 배치 저장·메모리 제한 | 원본 스트리밍, 배치 크기, 작업별 ORM context 수명 관리 | 전체 원본 대사 유지·peak RSS와 시간 비교 |
| E1-02 | 워커 확장 | 1→2→4개 프로세스, 동시성·DB pool 제한 | 처리량·대기시간·DB 잠금, 중복 효과 0 |
| E1-03 | 처리 속도 조절 | 큐 대기량·가장 오래된 job 나이 기준 수집 감속 | 유입 종료 후 정해진 관측 내 backlog drain |
| E1-04 | 외부 API 호출 제한 | 연결별 허용 호출량, 429·Retry-After, timeout | 설정된 상한 준수, 영구 재시도 방지 |
| E1-05 | 큐 분리·우선순위 | 수집/작업/집계 분리, 집계가 작업 생성을 독점하지 않게 함 | 업무별 지연 측정, 일반 작업 기아 방지 |
| E1-06 | 실패 job 운영 | 실패 이유·실행 이력·일괄 재시도·예산·중지 | 수정 가능한 오류와 영구 오류 분리 |
| E1-07 | Redis 보존·복구 | AOF 등 영속화, noeviction, 메모리 경보, DB 미완료 재대사 | Redis 재시작·큐 손실에도 DB 결과 복구 |
| E1-08 | 캐시 | 상품/집계 조회 캐시, TTL·무효화, cache-aside | DB 정합성과 stale 허용 범위·hit ratio 측정 |
| E1-09 | 증분 집계 | 날짜 전체 재계산 baseline→완료 이벤트 증분 반영 | 재처리·역전·재계산 대사 일치 |
| E1-10 | 외부 변경 수집 | updatedAt/버전이 있는 실제 또는 모의 source의 증분 변경 | 체크포인트 동률·늦은 변경·배정 후 수정 정책 시험 |
| E1-11 | DB 조회 최적화 | 인덱스·커서 페이지·N+1 제거·실행계획 | 쿼리 수·p95·인덱스 비용과 전후 비교 |
| E1-12 | 안정적인 종료·재배포 | 진행 job 종료/복구, migration·API 호환 | 처리 중 배포 후 업무 불변 조건 유지 |
| E1-13 | 관측과 추적 | requestId→order→task→event→job 추적 | 대기열 적체·실패·느린 DB를 원인별 구분 |
| E1-14 | 파생 부하 재생 | ID remap으로 100만 독립 주문, 고정 seed | 실제 원본/파생 분리, 참조·수량 대사 유지 |

캐시와 작업 큐의 Redis는 운영 확장 시 서로 다른 인스턴스로 분리합니다. 논리 DB 번호만 나누면 메모리 정책·장애 영역이 완전히 분리되지 않습니다. 재고·배정·이벤트 중복 여부의 최종 판단은 DB transaction·제약으로 수행합니다.

속도 향상을 이유로 ACK를 큐 수신 시점으로 앞당기려면 E1 범위에서 따로 설계해야 합니다. durable inbox 수신과 업무 반영 완료를 구분하는 새 계약·상태·최종 receipt 조회가 필요합니다. MVP의 APPLIED 의미를 그대로 둔 채 비동기로 바꾸지 않습니다.

## 3. E1 비교 실험

baseline은 MVP tag, 같은 원본·장비·측정 구간입니다. 최소 실험: 단건/배치 저장, 워커1/2/4, 호출 제한 유/무, 캐시 유/무 중 선택합니다. 모든 실험에서 원본·task·event·보고서 대사와 중복 효과 0을 유지합니다.

부하 시험은 누적 크기, 초당 입력률, 동시 단말 수를 별개 축으로 바꿉니다. DB가 병목인데 워커만 늘려 악화되면 그 결과도 기록합니다. 시뮬레이션이 실제 기업 트래픽을 대표한다고 쓰지 않습니다.

묶음 피킹의 창고 위치·동선 데이터는 Olist에 없으므로 직접 구성한 레이아웃으로 표시합니다. '실제 창고 이동거리 절감' 대신 고정 레이아웃 시뮬레이션 결과로 보고합니다.

작업 재배정 전 기존 단말의 현장 상태를 확인하는 업무 절차를 정의합니다. 서버의 lease 만료만으로 물리적 작업이 멈췄다고 판단하지 않습니다. 공유 재고를 오프라인에서 새로 예약·확정하는 문제는 E3 재고 정책의 일부입니다.

## 6. E3: 도메인·외부 연동

| ID | 확장 | 추가로 필요한 것 | 수용 기준 |
| --- | --- | --- | --- |
| E3-01 | 입고 | 입고 요청·예정/실수량·검수 정책 | 입고 기록→가용 수량 변경 추적 |
| E3-02 | 재고·예약 | inventory ledger·위치·예약·해제·동시성 | 과다 예약·음수 수량·중복 차감 검증 |
| E3-03 | 반품·교환 | RMA·회수·검수·재입고/폐기 규칙 | 출고·반품 연결과 감사 |
| E3-04 | 다중 창고 | 창고별 재고·작업·출고 가능 조건 | 창고 경계를 넘는 오반영 없음 |
| E3-05 | 외부 창고 어댑터 | API 계약·인증·상태 매핑·외부 키·조회 복구 | 기존 도메인 코드를 크게 바꾸지 않고 모의 A→B 교체 |
| E3-06 | 실제 샌드박스 | 서비스 계정·허용 범위·가용 일정 | 실제 HTTP 연동과 모의 결과 구분 |
| E3-07 | 운송장·배송 상태 | 배송사 계약·샌드박스 또는 연결 데이터 | 실제 라벨 구매와 모의 라벨 구분, 중복 발급 방지 |
| E3-08 | 단말 일련번호 생애주기 | 제품 모델·serial·출고·설치·회수·수리 이력 | 주문·개별 장비·매장 연결 추적 |
| E3-09 | 문서 기반 입력 | 공급 문서·OCR·상품 mapping·확인 절차 | 원문 근거·추출 정답·수동 수정량 평가 |

Olist에는 실제 창고 재고·장비 serial·수리·회수 데이터가 없습니다. 다른 공개 데이터가 이를 대체할 수 있는지 검토하고, 없으면 합성임을 표시합니다. 외부 시스템 API 접근 권한이 없다고 MVP를 기다리게 하지 않습니다.

Flexport 공식 문서에는 물리 재고를 이동하지 않는 sandbox가 안내돼 있으나 계정 전환을 지원팀에 요청하는 절차가 있습니다. 실제 계정·권한·약관·처리 가능 지역은 도입 시 다시 확인합니다. 프로젝트의 모의 API가 실제 Flexport 연동 실적이 되지는 않습니다.

## 9. 권장 선택

첫 포트폴리오 확장은 E1-01~04·06~07·13과 E2-01·06을 우선합니다. 데이터 처리·복구·자동화의 증거가 생기기 때문입니다. 시간이 더 있으면 E2-03·10·11, 이후 E3-05·06을 검토합니다.

첫 확장을 마칠 때도 MVP T-*를 회귀 실행합니다. 성능 개선으로 정확성·오프라인 보존·ACK 의미가 약해지지 않아야 합니다.
